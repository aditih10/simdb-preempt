What the OS scheduler can't see about your database — and whether your algorithm fixes it.

A general-purpose scheduler decides when to preempt a thread with zero visibility into whether that thread is holding a database lock or mid-validation. This dashboard runs that scenario as a discrete-event simulation and scores any custom preemption policy against it, so you can tell if a new algorithm actually helps before touching a kernel.

layer-gap closure score

100 means a policy fully closes the gap and matches the no-preemption ideal. 0 means it's no better than a lock-blind OS scheduler. Below 0 means it's actively worse. This is the single number to check when you're deciding whether your new algorithm is worth the complexity.

Every score above comes from the same interface — subclass PreemptionPolicy, decide when to defer a preemption, re-run. No kernel patch, no real DBMS instrumentation, results in seconds.

simdb_preempt_v2.pyzero dependencies
class GracePeriodPolicy(PreemptionPolicy):
    # example included in the simulator —
    # this is the "grace_period" line in every chart above
    name = "grace_period"

    def __init__(self, max_grace_ms=1.0):
        self.max_grace_ms = max_grace_ms

    def should_defer(self, core, env):
        # True = skip this preemption attempt
        if not core.critical:
            return False
        elapsed = env.now - core.critical_since
        return elapsed < self.max_grace_ms

Add the class, list it in POLICIES_TO_TEST, and re-run python3 simdb_preempt_v2.py. The simulator recomputes every chart on this page — abort rate, throughput, P99 latency, and the layer-gap score — for your algorithm alongside the three built-ins, using the exact same workload and random seed so the comparison is fair.

Everything your policy needs is on core: whether it's in a critical section right now, and how long it's been there. No access to the real OS or a live DBMS is required — the whole point is that you can validate an idea before it's worth building a kernel patch for.
